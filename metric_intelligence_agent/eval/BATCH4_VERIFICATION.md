The suite is a single versioned JSON document with source_id and cases. Each case contains

logical types, nonnegative finite tolerances, exact integers, unique keys, row-independent
comparison and extra columns allowed by default. Invalid/unknown fields, duplicate IDs or
questions, invalid layer names and unsupported ordering fields are rejected.

## Independent golden provenance and runtime construction

The candidate helper runs owner-authored SELECT references through `DuckDBConnector` in
read-only mode. A new output path is mandatory; existing reviewed files cannot be overwritten.
Every generated candidate is unapproved. Manual cases retain explicit owner-supplied rows
and review provenance. Only the owner can attest approval by editing the approval fields
after independent review; this is not a cryptographic approval mechanism.

Provenance records source identity, DB SHA-256, consumed-context file checksums and combined
hash, suite-definition checksum, expected-row checksum and DuckDB version. Suite definitions
include reference SQL, metric definition/formula/exclusions/grain and tolerance rationale.
The live report additionally hashes the entire approved suite. Normal evaluation refuses
any mismatch before a model call and never regenerates goldens. Freshness reports provenance
drift plus per-case reference discrepancies without model calls or fixture writes. Manual
references cannot be automatically re-executed and explicitly fail automatic freshness.

Production reuse is direct: `DuckDBConnector.connect`, `load_context(context_dir=...)`,
`load_table_layers`, `build_graph`, `run_question`. No Streamlit session state, special graph,
source activation, cached answers or new model configuration is involved. Runtime calls
retain Batch 2 validation/retry and Batch 3 model/trace semantics.

`query_log.run_type` is already VARCHAR. Accepting `custom_eval` is only an additive logger
validation change; no migration is necessary. Old values/history remain valid. Runtime
model, SQL, flags, layer, trace, tokens, cost and run identity use existing fields. Goldens
and comparison outcomes are not added to the database. Reports link outcomes to run IDs.

## Report contract

The JSON report contains version/status/start time, source/context/suite provenance, cases,
and summary. Cases include ID/question, overall pass, independent result match, terminal
verification, optional layer match, diagnostics, run ID, expected fixture ID/checksum,
SQL, attempts, model, flags, layer, runtime errors, trace, non-attempt usage, tokens/cost.
Full result DataFrames and expected data are omitted. Summary contains total, passes,
failures, pass rate, model, correct-but-not-verified, incorrect-result and layer-only-failure
counts. See the guide for exact JSON key names.

Correct data with invalid runtime status fails overall; model semantic approval does not
substitute for an independent result match. Layer enforcement is optional per case and
uses authoritative custom mappings. Terminal failures allow later cases to run; a service
exception stops with an explicit incomplete/error report and releases connections.
Private reports may contain SQL or diagnostic values and belong in ignored/local storage.
