# Reviewed local custom evaluation

TPC-H remains `python -m eval.run_eval`. Custom evaluation is a separate, explicit
DuckDB-file workflow; it does not discover local databases, activate a Streamlit source,
import setup pass/fail decisions, or create missing business context.

Keep the private database, context, suites and reports under gitignored `local_eval/`
or outside the repository. Do not commit private inputs. All paths below are placeholders;
no jaffle_shop artifacts or answers are supplied by this repository.

## Owner inputs and workflow

Supply:

1. The actual, checkpointed DuckDB database file. Close other writers first.
2. The reviewed context directory containing `table_catalog.md`, `schema.sql`,
   `metric_definitions.yaml` (preferred; legacy `metric_definitions.md` accepted), and
   analyst-owned `layer_classifications.json`. No demo fallback or global date range
   is used. Only the metric file actually selected by production context loading is hashed.
3. A JSON suite of independently written questions, metric contracts, reference SQL
   and/or manually reviewed expected rows. Setup validation questions may be copied
   by the owner as candidates; setup approval is not evaluation ground truth.

Write a template using the schema below, then explicitly generate a **new** candidate:

```powershell
python -m eval.custom_golden --candidate --db local_eval/source.duckdb --context-dir local_eval/context --suite local_eval/template.json --output local_eval/candidate.json
```

The helper uses the existing read-only DuckDB connector, never a model. SQL references
must return canonical column names. It executes the reference queries and freezes their
rows; manual cases must already provide explicit expected rows. It never overwrites an
existing file and always writes `approval.status=requires_owner_review`.

Review the formulas, exclusions, joins, grain, reference SQL, expected rows, tolerances,
source identity and hashes independently. Reference SQL must use the supplied database
and be deterministic; external files/services are not covered by its database fingerprint.
Approval is an owner attestation, not a cryptographic signature or an automated judgment.
Copy the reviewed candidate to `local_eval/reviewed.json`, then set:

```json
"approval": {
  "status": "approved",
  "reviewer": "owner identity",
  "note": "Describe the independent reference/result review performed"
}
```

Do not edit checksums to suppress drift. If definitions, context, data or expected rows
change, generate and review a new candidate. Candidate generation rejects malformed
contracts; normal evaluation also requires nonempty reviewer and approval notes and
matching provenance before any model call.

```powershell
python -m eval.custom_golden --check --db local_eval/source.duckdb --context-dir local_eval/context --suite local_eval/reviewed.json
python -m eval.run_custom_eval --db local_eval/source.duckdb --context-dir local_eval/context --suite local_eval/reviewed.json --report local_eval/reports/run-001.json
```

The report argument is optional; default is a new UUID-named file in
`local_eval/reports/`. Existing report paths are rejected before model calls.
Live evaluation requires the usual `OPENAI_API_KEY`; `OPENAI_MODEL` and the attempt budget
retain production behavior. Neither command writes the source database or regenerates
goldens during evaluation. Run types remain distinct: `adhoc`, TPC-H `eval`, and
`custom_eval`; the latter only extends logger validation over the existing VARCHAR column.
No schema migration or rewrite of prior history is required.

## Suite version 1

The following is a **synthetic schema illustration**, not a jaffle_shop question or answer.
`expected_rows`, `provenance` and `approval` are generated by the candidate helper; a template
can omit them for SQL cases. All other fields shown below are required except aliases,
exact_schema and expected_layer. Unknown fields are rejected rather than ignored.

```json
{
  "version": 1,
  "source_id": "owner-chosen-stable-source-id",
  "cases": [
    {
      "id": "monthly-example",
      "question": "Owner-reviewed question goes here",
      "result": {
        "keys": {"month": {"type": "month", "aliases": ["period"]}},
        "values": {
          "revenue": {"type": "number", "aliases": ["sales"], "abs_tol": 0.005, "rel_tol": 0}
        },
        "exact_schema": false
      },
      "expected_layer": "aggregated",
      "reference": {"kind": "sql", "sql": "SELECT month, SUM(amount) AS revenue FROM synthetic_table GROUP BY month"},
      "metric": {
        "definition": "Reviewed metric file and section",
        "formula": "SUM(amount)",
        "exclusions": "Explicit exclusions, or none",
        "grain": ["month"]
      },
      "tolerance_rationale": "Accept correctly rounded two-decimal reporting",
      "notes": "Independent reference authorship/review details"
    }
  ]
}
```

Expected rows are a nonempty list of objects containing exactly the canonical key/value
columns. A scalar has `keys={}` and exactly one row. Key types: `text`, `date`, `year`,
`month`, `integer`, `number`; metric values: `integer` or `number`. Integer tolerances
must be zero. All numeric expected values and tolerances must be finite. Null expected
values, empty golden results and ordering enforcement are unsupported in version 1;
the Batch 1 comparator is reused unchanged. Rows are order-independent, extra output
columns are allowed unless exact_schema=true, aliases are explicit and case-insensitive,
and ambiguous matches fail. There is no fuzzy matching or literal SQL comparison.
Expected layer is optional; when present it must be aggregated, fact or dimension and
uses Batch 3 physical-source reporting with analyst classifications.

Case IDs and normalized question text must be unique. Grain must equal the declared key
names in order. Metric definition/formula/exclusions, notes and tolerance rationale must
be nonempty. A manual case uses `reference={"kind":"manual","note":"Independent review details"}`
and explicit `expected_rows`; it can be evaluated after owner approval, but automated
freshness reports it as not verifiable and requires owner re-review. References and expected
rows are embedded, so there are no secondary SQL/golden paths that could be missing or stale.

## Provenance, freshness and output

Candidate provenance includes source ID, streaming SHA-256 of the DB file, hashes of the
four consumed context files, aggregate context hash, case-definition checksum, frozen-row
checksum, and DuckDB version. Case-definition hashing includes question, contract, SQL or
manual reference, metric definition/formula/exclusions/grain, notes and tolerance rationale.
It excludes expected rows (separately hashed) and approval/provenance to avoid circular hashes.
Live reports additionally hash the complete reviewed suite, including approval.

`--check` validates the suite, reports provenance mismatch, and re-runs each SQL reference
against frozen rows using the Batch 1 comparator, identifying every mismatching/error case.
It makes no model calls, never updates fixtures, and exits nonzero on any drift or manual
case that cannot be checked. Live evaluation rejects any provenance mismatch before model
execution. DB hashes are deliberately strict: even a content-preserving file rewrite may
require a new review. Context hashes are byte-sensitive. Do not modify inputs concurrently.

Each live report has version, status, start time, DB/context/suite provenance, case outcomes
and summary. Per case: ID/question, overall pass, result match, terminal verification,
optional layer match, failure reasons, logged run ID, fixture ID/checksum, final SQL,
attempt count, model, success/valid/out-of-range flags, layer, runtime errors/reason,
attempt trace, non-attempt usage, token totals and estimated cost. No DataFrame or frozen
expected rows are included. Diagnostics and SQL may contain private values, so reports
are private too. Persisted run records contain runtime metadata only, not golden data.

Summary fields: total, passes, failures, pass_rate, model,
result_correct_but_not_verified, incorrect_result and layer_only_failure.
Overall pass requires independent correctness, explicit successful/valid/in-range terminal
flags, and the expected layer when declared. Semantic-review approval alone never passes.
Terminal query failures continue to later cases. An exception outside terminal graph state
(for example authentication failure) stops the run and leaves an error report with completed
cases; it must not be interpreted as a complete accuracy measurement.

CLI exit codes: 0 for success/all pass, 1 for comparison failures, 2 for rejected input.
Unexpected runtime/service errors may produce a traceback and an error report.
The normal custom path is the same read-only connector, `load_context`, `load_table_layers`,
`build_graph` and `run_question` used by production. No Streamlit session state is needed.
